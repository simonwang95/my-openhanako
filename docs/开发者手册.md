## 1. 架构总览

### 1.1 技术栈

| 层级 | 技术 |
|------|------|
| 桌面端 | Electron 42 |
| 前端 | React 19 + Zustand 5 + CSS Modules |
| 构建 | Vite 7 |
| 服务端 | Hono + @hono/node-server + @hono/node-ws |
| Agent 运行时 | Pi SDK（@earendil-works/pi-*，postinstall 打补丁） |
| 数据库 | better-sqlite3（WAL 模式） |
| 测试 | Vitest |
| 国际化 | 5 语言（zh / en / ja / ko / zh-TW） |
| Node.js | >= 24.12.0 < 25（CI 使用 24.15.0） |

### 1.2 运行模型

```
┌─ Electron 主进程（desktop/）────────────────┐
│  bootstrap.cjs → main.cjs                   │
│  spawn Server 子进程（独立 Node.js）         │
│  渲染进程（React）⇄ WebSocket ⇄ Server      │
└──────────────────────────────────────────────┘
┌─ HanaAgent Server（server/，独立进程）──────┐
│  startServer 组合根（Hono + @hono/node-ws） │
│  ├─ HanaEngine（core/，薄门面）             │
│  │   └─ 各 Manager（Agent/Session/Model/   │
│  │      Plugin/Skill/Cron/Bridge/…）       │
│  ├─ Hub（hub/，后台调度，独立于会话）       │
│  └─ 路由（server/routes/，约 46 个）        │
└──────────────────────────────────────────────┘
        数据全部落盘于 HANA_HOME（~/.hanako）
```

- **Server 是独立 Node.js 进程**（spawn，非 fork，不在 Electron 主进程内），因此 `better-sqlite3` 不需要 electron-rebuild；
- 渲染进程与 Server 通过 **WebSocket** 通信（无 IPC 传递业务数据）；启动后 Server 写 `server-info.json`（端口 + token）供桌面端轮询连接；
- **Engine 是"薄门面"**：构造器以依赖注入装配全部 Manager，Hub 启动后经回调反向注入；`init()` 执行一串 best-effort 幂等迁移；
- **Hub 负责后台任务**（心跳巡检、定时任务、频道路由、Agent 间通信、DM 路由），独立于当前聊天会话运行；
- 前端有 **OTA 热更新**机制（renderer 归档 + 签名校验水线），`hana bundle pull` 与桌面端共用 `shared/artifact-core/`。

## 3. 核心机制剖析

### 3.1 引擎编排与 Agent 模型

- `HanaEngine` 是**薄门面**：构造器依赖注入装配全部 Manager（Preferences / Model / Speech / Media / MCP / SessionCoordinator / ConfigCoordinator / ChannelManager / AgentManager / BridgeSessionManager / Notification / TaskRegistry / Terminal / Checkpoint / StudioCron / Plugin），Hub 启动后经 `setHubCallbacks` 反向注入；`init()` 执行一串 best-effort 幂等迁移（配置作用域、provider YAML、凭证权限自愈等）；
- **"Agent 就是文件夹"**：`agents/<id>/` 即数据目录（§2.11），全部是用户可直接读改的 YAML / Markdown 文件；人格文件惰性落盘（缺失时运行时按 `agent.resolveLocale()` 现选 lib 模板，用户改语言后未定制人格自动跟着换）。

### 3.2 记忆系统（lib/memory/）

**记忆类型**：固定记忆 `pinned.md`；事实库 `facts.db`（SQLite + FTS5，无向量）；会话摘要 `summaries/`；滚动摘要（memory-reflection v3 模板）；编译产物 `today/week/longterm/facts.md`；深度记忆（`deep-memory.ts`：每日对"脏"会话做 snapshot diff，LLM 拆成带标签元事实）；dream（对编译记忆做原子化/去重/优化/校验，revision-store 支持回滚）。

**"记忆编译"传送带（compile.ts v4）**：

```
会话摘要 → compileDaily（LLM 蒸馏成两三句日记）
        → assembleWeekFromDaily（纯文件装配最近 6 个逻辑日，零 LLM）
        → rollDailyWindow（滚出窗口的 daily fold 进 longterm）
        → compileEditableFacts（增量编译 + 水位线跟踪）
        → assemble（拼 memory.md，受 token 预算约束）
```

**调度（memory-ticker.ts）**：每 10 轮 → 滚动摘要 + compileToday；会话结束 → final 摘要；逻辑日切换 → 全流水线 + deep-memory + dream。

**检索**：`search_memory` 工具 = 标签匹配 + 日期过滤 + FTS5 兜底；频道会话默认看不到其它频道事实。

**衰减**：高斯衰减 `score = score × e^(-λ × t²)`（`decay_per_day` 默认 0.02 ≈ 14 天归零）；被 hit 过的记忆重置衰减起点。

### 3.3 安全沙盒（lib/sandbox/）

**双层隔离**：

1. **PathGuard 路径 ACL**（`path-guard.ts`）：四级 `BLOCKED` / `READ_ONLY` / `READ_WRITE` / `FULL`；先 realpath 解符号链接再匹配区域。操作要求：read ≥ read_only、write ≥ read_write、delete/stage = full。区域定义（`policy.ts`）：
   - BLOCKED：auth.json、models.json、browser-data/ 等凭证；
   - READ_ONLY：config.yaml、identity.md、AGENTS.md、user/、skills/ 等；
   - READ_WRITE：Agent 的 memory/sessions/desk/heartbeat/book/activity/avatars、channels/logs/uploads、工作区根；
   - FULL：full-access 模式。
2. **OS 沙盒**：macOS Seatbelt（生成 SBPL profile：deny default + 全局可读 + 可写路径 + 网络可关，sandbox-exec 执行）；Linux Bubblewrap（mount 命名空间、系统目录只读，缺 bwrap 时 **fail-closed** 拒绝直跑）；Windows restricted-token（`hana-win-sandbox.exe` helper 进程按显式文件读写授权运行，读不按 ACL 投影）。

**设置对应**：全局偏好 `sandbox` 开关 + `sandbox_network`（默认开）；策略恒按 standard 构建，wrapper 运行时按开关动态 bypass（切换偏好无需重建 session）；另保护工作区 `.git` 与 session-files 只读。

### 3.4 定时任务与心跳

- **Cron 已 Studio 化**：任务存 `~/.hanako/studios/<id>/desk/cron-jobs.json` + `cron-runs/*.jsonl`（`studio-cron-service.ts` 首次访问时把旧 per-agent 任务迁移进来）；
- **三种触发器**：`at`（一次性）/ `every`（间隔）/ `cron`（表达式）；
- **调度为确定性层**（`cron-scheduler.ts`）：每分钟检查到期（无 LLM），到期创建后台 Agent session 执行（默认 20 分钟超时、per-job 锁 + abort）；任务必带 actorAgentId 与 executionContext；
- **心跳**（`scheduler.ts` + `heartbeat.ts`）：每个有 desk 的 Agent 并行运行、不依赖焦点 Agent；默认 31 分钟、默认关闭。两阶段：工作台文件变化检测（快照差量，排除 Agent 自身输出目录防自触发）+ 笺扫描（工作区根 + 一级子目录的 `jian.md`，指纹比对后隔离执行）；
- **笺（jian.md）**：内容 = 用户指令 + 执行日志（`<!-- exec-log -->` 分隔）；Agent 独立执行、不询问用户，用 `jian_update_status` 回写状态（in_progress/completed/skipped/failed），"完毕且语义一致"则跳过；
- 自动化统一包装为 "Agent Run" prompt（`agent-run-automation.ts`，含固定通知/插件动作）；`activity-store` 记录执行元数据（上限 100 条，自动清理旧记录及会话文件）。

### 3.5 Agent 间频道与 DM

- **频道 = MD 文件** `ch_{id}.md`（`~/.hanako/channels/`）：frontmatter（id/name/description/members）+ 消息流（`### 发送者 | 时间戳`），最少 2 名 Agent 成员，纯文件无数据库（`channel-store.ts`）；每个 Agent 的 `channels.md` 记"加入哪些频道 + 读到哪"（书签时间戳）；
- **调度**（channel-ticker / channel-router）：新消息 → 中断当前执行 → 送达所有成员（未读窗口 20 条，超出丢弃计数）→ 恢复检查点；`@提及` 解析为调度提示而非可见性规则；提醒到期随机点醒一名成员基于频道 Truth 主动发言；
- **DM**（dm-router）：1v1，回复写回双方 `dm/` 文件；3 轮上限 + 10 秒冷却防无限对话；DM phone session 复用普通会话提示词但不进记忆系统。

### 3.6 多平台桥接（lib/bridge/）

- 每平台一个 adapter，共享 engine 的 `_executeExternalMessage`（`bridge-manager.ts`）：Telegram（HTTP API）、飞书（WebSocket 长连接 + 卡片流式渲染）、QQ（自建 WebSocket 网关）、微信（ilink HTTP 轮询，持久化同步缓冲）、钉钉（stream）；
- **路由**：sessionKey 前缀数据驱动映射（`session-key.ts`：`tg_dm_` / `tg_group_` / `fs_` / `dt_` / `qq_` / `wx_` + `chatId@agentId`）；BridgeSessionManager 维护 bridge session 索引，把外部消息注入对应 session 执行（注入 bridge 上下文、媒体转码、按平台归一权限模式）；回复经 adapter 回发（流式/媒体经 MediaDeliveryService，幂等去重 10 分钟 TTL）；
- **owner-policy** 判定平台 owner（微信 DM 即 owner），决定通知投递目标。

### 3.7 会话管理（core/session-*.ts）

- **存储**：`sessions/<id>.jsonl`，首行 session 头，每行一个条目；超限行（>1MB）读时投影截断；`session-manifest/` 存会话元数据与分支头（含启动迁移）；
- **压缩**：三层——SDK 级、运行中压缩（保缓存前缀）、按需 LLM 摘要（compactSessionWithCachePreservation）；LLM 不可用时回退有损本地压缩，硬截断阈值 0.85；
- **分支**：单个 JSONL 是条目树，分支头（当前叶）持久化在 manifest，切分支 = 选叶；fork 会复制会话文件/媒体/插件配置/记忆基线等关联状态；
- **归档**：移入 `sessions/archived/`，生命周期 active/archived/deleted。

### 3.8 数据快照与检查点（data epoch）

- **data epoch = 破坏性格式变更的版本机制**：stamp（已提交纪元）+ journal（过渡日志）+ checkpoint；启动时协调器判定 stamped-new / adopted-legacy / steady / transition-committed，**拒绝纪元降级**（`data-epoch-coordinator.ts`）；
- **检查点**（`data-epoch-checkpoint-provider.ts`）：迁移前对受影响存储做字节可验证快照（SQLite online backup 折叠 WAL，其余逐文件拷贝 + sha256），存 `data-epoch-checkpoints/{transitionId}/`，保留 2 份、上限 2GB；
- **恢复**（`data-epoch-restore.ts`）：日志化恢复事务——恢复前字节移入 quarantine（永不删除）、拷回检查点字节、逐文件对账、再重发 stamp；当前尚无用户界面（库级入口，CLI `hana data` 提供维护面）；
- 生产目前 epoch=1、迁移表为空（`data-epoch-migrations.ts`）——属预留基础设施；
- 注意区分：`CheckpointStore`（`lib/checkpoint-store.ts`）是**工具级文件备份**（工具改文件前存原内容，供回滚），与 data epoch 无关。

### 3.9 权限与执行边界

- **会话权限档**（`session-permission-mode.ts`）：`auto`（默认：只读工具放行，副作用工具交 LLM 审查）/ `operate`（免审批）/ `ask`（人工审批）/ `read_only`（计划模式，拦截写操作并标明拦截层与解锁方式）；bridge/automation 会话只允许 auto/operate/read_only；
- **审批**（`approval-gateway.ts`）：auto 档的 review 由小工具模型初审、可 escalate 给大工具模型终裁，返回 allow / deny_and_continue / ask_user / escalate（auto 下 ask_user = 不执行）；硬安全策略（`safety-policy.ts`）先行拦截凭证暴露、工作区外破坏性删除、stage_files 工作区边界（双重 canonical 校验）；
- **能力授权**（`capability-policy.ts`）：远程调用者——本地 owner 自动放行，否则需有效 grant（grant-registry：capability + 传输方式 + scope 匹配）；
- **执行边界**（`execution-boundary.ts`）：绑定 serverNodeId + studioId 的冻结描述符；**执行租约**（`execution-lease-service.ts`）：非本地 principal 写文件前发 lease（TTL 5 分钟、snapshot_before_write 备份），写时消费、可吊销；
- **subagent 固定边界**独立于权限档：禁用 subagent/workflow/session/长期记忆写/notify 等（防自递归与副作用）。

### 4.1 启动链

```
main-full.ts
  → 同宅互斥闸（token 探测 server-info.json，防同 HANA_HOME 双内核）
  → data-epoch 事务闸（纪元降级保护）
  → 端口选择 / loopback 自愈回退
  → ensureFirstRun 播种（core/first-run.ts）
  → HanaEngine 初始化
  → initPlugins
  → Hub 调度启动
  → 首个 session（HANA_CREATE_STARTUP_SESSION=0 可跳过）
  → 写 server-info.json（桌面端轮询连接，无 IPC）
```

**鉴权**：Bearer token（`HANA_TOKEN` 或随机生成）+ WS ticket；CORS / 传输层分类 / 插件 iframe ticket / 资源 ticket 均在 `app.use("*")` 中间件链（`server/http/*`）。

### 4.2 WebSocket 协议（ws-protocol.ts）

| 方向 | 消息 |
|------|------|
| 客户端 → 服务端 | `prompt`、`interject`、`abort`、`resume_stream`、`compact` |
| 服务端 → 客户端（流式） | `text_delta`、`mood_*`、`thinking_*`、`tool_start/end`、`turn_end`、`status`、`stream_resume`（按 seq 续传）、`content_block`（统一内容块：file/媒体/截图/卡片/确认等）、`bridge_status` 等 |

WS 是桌面端 / CLI / 移动端共享的实时面。

### 4.3 两个组合入口

- `main-full.ts`：完整产品（注册闭集路由 + 内置媒体适配器）；launch.js / CLI / 桌面 dev 都 spawn 它；
- `main-open.ts`：开源 composition（`startServer({})`），供 `build-server-open.mjs` 打包，带 `export-manifest.json` 白名单断言。

组合在进程入口**静态决定**，不是运行时开关。

## 6. 插件开发

### 6.1 Manifest 结构

`plugins/<id>/manifest.json`（可选但推荐）：

```json
{
  "id": "my-plugin",
  "name": "My Plugin",
  "version": "0.1.0",
  "description": "…",
  "trust": "restricted",
  "hidden": false,
  "capabilities": ["resource.read"],
  "sensitiveCapabilities": [],
  "activationEvents": ["onStartup"],
  "contributes": {
    "configuration": { "properties": { } }
  },
  "dev": { "scenarios": [] }
}
```

插件可贡献（`contributes` 声明）：`tools/`、`skills/`、`commands/`、`agents/`、`routes/`（HTTP）、`extensions/`（Pi SDK 事件）、`providers/`、page/widget/SettingsTab（UI）、configuration、chat.surface、动态工具、后台任务。

### 6.2 两级权限

| 级别 | 说明 |
|------|------|
| `restricted`（默认） | 未声明 trust 一律按此。可贡献工具/命令/技能等；代码在主进程运行（非代码级沙盒，限制的是"系统给的扩展接口"，事件总线只有 emit/subscribe/request） |
| `full-access` | 额外获得生命周期、HTTP 路由、Extensions、Providers、UI 页面、动态工具、后台任务；需 manifest 声明 `"trust": "full-access"` 且用户在设置页开启"允许全权插件"（开关关闭时完全不加载） |

敏感能力按 manifest `capabilities` 声明 + 用户授权双重校验（403 `PLUGIN_CAPABILITY_NOT_DECLARED` / `NOT_GRANTED`）。

### 6.3 安装与管理

- 拖拽文件夹或 zip 到设置 → 插件安装区 / 文件选择器 / 放入 `~/.hanako/plugins/`；
- 启用/禁用/删除/同名升级即时生效，无需重启；
- 私有数据在 `~/.hanako/plugin-data/<pluginId>/`；
- 安装备份与版本管理：`lib/plugin-install-backups.ts`、`plugin-versioning.ts`、`plugin-marketplace.ts`。

### 6.4 开发循环

- `plugins-dev/` 槽位 + EventBus（`plugin.dev.install/reload/…`）或 HTTP（`POST /api/plugins/dev/…`）；
- Agent 可见 dev 工具默认需用户在设置中开启；
- 文档：`PLUGINS.md`（中文，含插件文件贡献规则）、`PLUGIN_SDK.md`；SDK 包在 `packages/plugin-sdk` 等；
- 内置技能 `hana-plugin-creator` 可引导创建新插件（脚手架 + 开发向导）。
